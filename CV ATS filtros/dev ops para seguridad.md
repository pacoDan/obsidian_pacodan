Sí. Un perfil previo de DevOps puede ser un muy buen punto de partida para GRC, especialmente si el GRC está orientado a IT, ciberseguridad, cloud o tecnología. No reutilizaría el perfil completo, sino determinadas competencias y experiencias.

¿Qué se puede reutilizar directamente?
1. Conocimiento técnico de infraestructura

Es probablemente el mayor beneficio.

De DevOps se puede aprovechar experiencia en:

Cloud: AWS, Azure, GCP.
Servidores, redes y sistemas operativos.
Bases de datos.
Contenedores y Kubernetes.
CI/CD.
Git y control de versiones.
Infraestructura como código.
Monitoreo y logging.
Gestión de configuraciones.

Esto le permite al analista GRC entender técnicamente qué está evaluando, algo muy valioso frente a un perfil puramente administrativo.

Por ejemplo, ante un control que dice "los accesos privilegiados deben revisarse periódicamente", alguien con background DevOps puede entender rápidamente qué significa un usuario privilegiado, dónde están esos accesos, cómo se gestionan y qué evidencia técnica debería existir.

2. Seguridad y controles técnicos

Si el perfil DevOps ya tenía prácticas de DevSecOps, hay mucho para reutilizar:

Gestión de secretos.
Vulnerability management.
Scanning de código/imágenes.
Gestión de accesos.
MFA.
Hardening.
Patching.
Logs.
Gestión de incidentes.
Seguridad de pipelines.
Seguridad cloud.
Control de cambios.

Esto puede convertirse directamente en conocimiento para IT GRC.

3. Gestión de cambios

La experiencia DevOps suele estar muy relacionada con:

Change Management.
Releases.
Aprobaciones.
Pull requests.
Trazabilidad.
Separación entre desarrollo y producción.
Rollback.
Evidencias de cambios.

Todo esto es muy reutilizable para controles de IT General Controls (ITGC).

Por ejemplo:

DevOps: "Toda modificación a producción pasa por un Pull Request y pipeline."

↓

GRC: "Existe un control de gestión de cambios que requiere aprobación y evidencia previa a la implementación."

El profesional ya conoce cómo funciona realmente el proceso, no solamente la teoría del control.

4. Automatización

Esta es otra ventaja enorme.

Un perfil DevOps probablemente tenga capacidad para:

Crear scripts.
Automatizar tareas.
Consultar APIs.
Trabajar con SQL.
Manipular datos.
Generar reportes.
Automatizar validaciones.
Integrar herramientas.

En GRC esto permite pasar de un enfoque muy manual a uno de Continuous Controls Monitoring (CCM) o, al menos, automatizar parte de las pruebas de controles.

Por ejemplo, en lugar de revisar manualmente 500 usuarios:

DevOps/GRC puede automatizar:

IAM → extracción de usuarios → reglas de control → identificación de excepciones → reporte

Eso es un diferencial muy fuerte para un perfil GRC.

¿Qué habría que agregar al perfil?

Acá está la transformación importante.

No intentaría convertir simplemente al DevOps en "DevOps que hace auditoría". Hay que incorporar el lenguaje y la metodología GRC.

El gap principal estaría en:

Risk Assessment.
Risk & Control Matrix.
Control Design / Control Effectiveness.
Evidencias de control.
Testing de controles.
Auditoría.
Compliance.
Políticas y procedimientos.
Gestión de hallazgos.
Planes de remediación.
Risk Acceptance.
Governance.
Marcos regulatorios.
ISO 27001 / ISO 31000.
COBIT / COSO.
Conceptos de ITGC.
Un perfil especialmente interesante: DevOps → IT GRC

De hecho, yo diferenciaría entre GRC generalista y IT GRC.

Para un GRC generalista, el background DevOps es útil, pero puede quedar bastante alejado del día a día.

Para IT GRC / Technology Risk / Cyber GRC, en cambio, el background DevOps puede ser un diferencial muy importante.

El perfil podría evolucionar así:

DevOps

→ Cloud / Infrastructure
→ CI/CD
→ Automation
→ Security
→ IAM
→ Monitoring
→ Change Management

+ GRC

→ Risk
→ Controls
→ Compliance
→ Audit
→ Evidence
→ Control Testing
→ Remediation

= IT GRC / Technology Risk Analyst

¿Qué NO reutilizaría como requisito?

Evitaría trasladar al perfil GRC requisitos puramente técnicos de DevOps que no tengan relación con sus responsabilidades.

Por ejemplo, no pondría como requisito principal:

"Experiencia administrando Kubernetes."
"Experiencia desarrollando pipelines complejos."
"Terraform avanzado."
"Docker avanzado."
"Linux avanzado."

Sí pondría, en cambio:

Conocimientos de infraestructura, cloud, CI/CD y herramientas de automatización, que permitan comprender y evaluar controles tecnológicos.

Así el conocimiento técnico pasa de ser la función principal a ser una herramienta para hacer GRC mejor.

Mi recomendación

Si estás construyendo el nuevo perfil JR de GRC a partir de un perfil DevOps existente, yo conservaría aproximadamente 30–40% del contenido técnico, pero reformulado, y agregaría un bloque fuerte de Risk, Controls, Compliance y Audit.

El resultado puede ser bastante atractivo: un Analista Jr. de IT GRC con background DevOps, que tenga capacidad para entender controles técnicos y además automatizar pruebas y reporting. Ese perfil puede tener bastante más potencial que un GRC JR puramente administrativo.
