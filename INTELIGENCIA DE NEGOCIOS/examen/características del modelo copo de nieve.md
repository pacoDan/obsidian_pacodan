El **modelo copo de nieve (Snowflake Schema)** es una técnica de modelado físico para bases de datos multidimensionales que se caracteriza por normalizar sus dimensiones organizándolas en niveles jerárquicos.

Sus principales características son:

- **Estructura por atributos:** A diferencia del modelo estrella (que agrupa toda una dimensión en una sola tabla), el modelo copo de nieve crea **una tabla _lookup_ por cada atributo** que conforma la dimensión. Por ejemplo, en lugar de tener una sola tabla de "Producto", tendrá tablas separadas para "Ítem", "Género" y "Categoría" vinculadas entre sí.
- **Alta normalización y baja redundancia:** Al estar completamente normalizado (asemejándose a una cuarta forma normal), **minimiza la redundancia de datos y ahorra un espacio significativo de almacenamiento** en la base de datos.
- **Mayor complejidad en las consultas (Uso de _Joins_):** Al desglosar la información, genera un mayor número de tablas en el modelo. Para consultar un dato en la parte alta de la jerarquía (como averiguar la categoría de un ítem vendido), el motor de base de datos se ve obligado a realizar **múltiples saltos o _joins_** entre las tablas. Esto puede ralentizar el rendimiento de las consultas y representar un problema si el motor relacional tiene un límite máximo de _joins_ permitidos por consulta.
- **Facilidad en el proceso de carga de datos (ETL):** Paradójicamente, a pesar de tener más tablas, **es más fácil de llenar**. El llenado se hace respetando el orden jerárquico de arriba hacia abajo (primero se llena la tabla padre, luego la hija vinculando el ID del padre, etc.), lo que evita tener que crear tablas auxiliares temporales para buscar combinatorias únicas y evitar incongruencias.
- **Menor comprensión para el usuario final:** Sus múltiples tablas y ramas jerárquicas lo vuelven **más difícil de interpretar y navegar para el usuario de negocios**, quien se pierde al tener que seguir la ruta de relación entre tantas tablas para conseguir un dato descriptivo.
- **Administración distribuida de cambios históricos:** Ante un cambio en las características de un elemento, las actualizaciones y la generación de nuevas Claves Subrogadas (SK) **se realizan de manera descentralizada** en las tablas específicas afectadas (y sus relaciones directas), en contraposición al modelo estrella, donde cualquier cambio impacta directamente a la tabla única central.

Adicionalmente, el modelo copo de nieve se puede subclasificar según las decisiones arquitectónicas sobre su **grado de normalización** para equilibrar el rendimiento:

1. **Completamente normalizado:** Es el modelo puro. Mantiene la mínima redundancia posible; cada tabla hija solo posee su ID, su descripción y el ID de su padre directo. Requiere el máximo número de _joins_ para leer los datos.
2. **Moderadamente normalizado:** Para reducir la penalización de los _joins_, cada tabla hija guarda internamente los IDs de **todos sus ancestros** (padre, abuelo, etc.). Esto ahorra saltos en la base de datos, pero introduce cierta redundancia que debe controlarse.
3. **Completamente desnormalizado:** Las tablas hijas arrastran no solo los IDs, sino también las descripciones de todos sus ancestros. Aunque reduce las consultas a un solo _join_ (asemejándose mucho a un modelo estrella en la práctica), ocupa muchísimo más espacio de almacenamiento y genera una gran redundancia de texto.
